# ETH 예측 가용성 재발 방지 구현 계획

상태: 사용자가 “어 재발 방지 수정”으로 구현·검증·배포를 승인함. 아래 계획에 따라 수정 중이며 결과는 implementation.md에 기록한다.
기준 코드: baf022d907512d3fdd79c819616095476c6e10b0.
긴급 복구는 기존 작업 재실행으로 완료했다. 이 문서는 아래 변경이 구현·배포됐다는 뜻이 아니다.

## 목표와 선택

새 발행이 실패해도 사용자가 이전에 공개된 유효한 예측을 날짜와 함께 볼 수 있게 한다.
현재 예측의 준비 상태와 파일 배포 확인을 분리하여, 0개 예측의 배포가 정상 복구로 보고되지 않게 한다.
발행 마감 직전의 복구 요청을 줄이되, 늦은 작업을 과거 시각으로 발행하는 방식을 허용하지 않는다.

| 경로 | 판단 |
|---|---|
| 기존 작업 재실행 | 이번 긴급 복구에 사용. 같은 장애의 재발 방지는 못 함 |
| 현재 모델을 유지하고 발행·화면·검증 경계 수정 | 이번 구현 범위로 제안 |
| 상시 실행 worker와 독립 scheduler 도입 | 가용성 요구와 외부 운영환경을 정한 후 별도 계획. 이번에 새 인프라를 만들지 않음 |

## 1. 공개 확인된 이전 예측을 카드에 유지

수정: forecast_site/public/events.js
검증: tests/test_event_frontend.py

현재 구간의 record가 없을 때 recent_issued에서 해당 구간의 최신 공개 확인 기록을 찾는다.
필수 자격:

- forecast_id가 있으며 선택 구간과 horizon_seconds가 정확히 일치한다.
- 공개 확인 시각이 유효하고, 미래 시각이 아니며, window_start보다 이르다.
- 목표 종료가 현재 시각 뒤이고 관측창·입력 기준 시각이 일관된다.
- 가격·확률이 유한하며 구간 순서와 확률 합이 유효하다.
- 백테스트 points, 공개 미확인 원장 기록, 늦게 공개된 기록은 대체 표시 후보가 아니다.

표시 결정:

| 상황 | 화면 |
|---|---|
| 현재 선택 구간의 발행값 존재 | 발행값 및 기존 신선도 표시 |
| 현재 발행 누락, 공개 확인된 만기 전 이전 값 존재 | Previous published forecast · Update delayed 및 실제 발행·기준·만기 시각 |
| 이전 값도 만기 경과 또는 자격 미충족 | Forecast unavailable |
| 다음 완전한 현재 묶음 도착 | 현재 예측으로 자동 복귀 |

이전 값을 current 배열로 옮기거나 새 generated_at·issued_at로 고쳐 쓰지 않는다.
가격·분위수·확률·모델·forecast_id·목표일은 원본 그대로 표시한다.
상단 상태는 Update delayed를 유지하며, 이전 카드 6개가 존재한다고 ready가 되지 않는다.
새로고침 후에도 서버가 이미 제공하는 recent_issued를 활용하여 동일한 결과가 나오게 한다.
30초 상태 갱신 시 만기를 다시 확인하여 만기 경과 카드를 현재 또는 유효 이전 예측처럼 계속 표시하지 않는다.

## 2. 배포 확인과 예측 준비 검증의 성공 기준 분리

수정: scripts/publish_events.sh, scripts/verify_event_site.py
검증: tests/test_event_recovery.py, tests/test_event_frontend.py

현재 --expected 검사는 정확한 파일·ID의 공개 확인 역할을 유지한다. 일부 발행값이 실제 공개됐다면 해당 기록의 공개 이력을 보존할 수 있어야 한다.
이 단계의 로그는 “payload published/verified”로 뜻을 명확히 한다.

그 후 공개 이력·원장 저장을 마치고 별도의 필수 준비 검사(--require-ready)를 수행한다.
정상 발행 작업의 최종 성공 조건:

- status=ready.
- 기대하는 시간 슬롯의 6개 구간이 정확히 하나씩 존재.
- 6개 forecast_id가 유일함.
- 입력 기준·생성·발행 시각과 원본 가격·확률 형식이 유효함.
- 공개 파일과 의도한 release_id 및 ID 목록이 일치함.
- HTML·JS가 현재 배포 소스와 일치함.

빈 결과나 부분 결과를 장애 상태로 공개하더라도 작업 전체를 정상 예측 성공으로 종료하지 않는다.
실패 상태의 원장·진단 artifact 보존은 계속 수행하며, 실패 판정 때문에 이미 공개된 개별 기록의 이력이 사라지지 않게 한다.

## 3. 마감 직전 복구 요청 차단과 실제 발행 시각 확인

수정: scripts/event_recovery.cjs, signal_pipeline/engine.py, signal_pipeline/ledger.py의 마감 오류 설명, 필요시 .github/workflows/event_hourly.yml
검증: tests/test_event_recovery.py, tests/test_event_pipeline.py

- 신규 복구 요청은 발행 마감인 :55까지 최소 5분을 확보하도록 :50 이전으로 제한한다.
  이는 이번 요청부터 추론까지 약 48초가 걸린 상황에 여유를 둔 운영 기본값이다. GitHub 실행 시작을 보장하는 SLA가 아니다.
- 현재 실행 중인 공유 작업 확인, 20분 cooldown 및 한 번의 dispatch 제한은 유지한다.
- 요청 직전 시각을 다시 확인하여 API 조회 중 흐른 시간까지 반영한다.
- 지연·대기 때문에 마감을 넘긴 경우 신규 발행을 중단하고 deadline 사유를 명시한다.
- engine.daily의 데이터 조회 기준(as_of)과 각 record의 실제 발행 시각을 분리한다.
  현재 코드는 함수 시작 시각을 issue(now=current)에 재사용하므로, 처리 도중 마감을 넘는 상황도 검증한다.
- 기존 예측의 불변성, 확정봉 사용, 실제 공개 전 관측창 시작 금지 원칙을 유지한다.
- 시간 슬롯이 바뀌면 이전 슬롯으로 날짜를 되돌려 발행하지 않는다. 다음 정상 창에서 최신 확정봉으로 발행한다.
- 시간별 작업에서 학습이나 전체 백테스트를 새로 실행하지 않는다.

## 4. 장애 회귀검증

관측한 장애를 직접 재현하는 검증만 추가한다.

1. current=[]이고 공개 확인된 이전 예측 6개가 있을 때 모든 구간이 날짜를 포함한 지연 카드로 표시되는지.
2. 이전 값의 ID·가격·확률·입력 기준·목표일이 표시 전후 동일한지.
3. 만기 경과, 공개 미확인, 늦은 공개, 잘못된 시각·수치의 기록을 사용하지 않는지.
4. 첫 페이지 로드, 새로고침, 연결 중단, 부분 발행, 완전한 새 발행 복귀의 상태 전환.
5. 이전 카드가 6개 있어도 current=0 또는 부분 발행이면 엄격한 준비 검사에 실패하는지.
6. :49:59 / :50:00 복구 요청 경계와 :54:59 / :55:00 실제 발행 경계.
7. 복구 요청은 마감 전이었지만 환경 준비나 추론 중 :55 또는 다음 시간으로 넘어간 경우 신규 발행 차단.
8. 원장과 실패 artifact 보존 후에 작업 최종 상태가 실패로 남는지.
9. 공개 payload와 ID 목록이 다르거나 원본 코드와 화면 파일이 다르면 복구 성공으로 처리하지 않는지.

관련 기존 테스트에 위 사례를 추가하고 CI에서 실행한다.
로컬 테스트 환경의 누락 의존성은 정상 실행 환경에 맞춰 해결하거나 기존 CI로 검증하고, 실행하지 못한 검증을 통과로 기록하지 않는다.

## 5. 구현·배포 순서와 완료 기준

계획 승인 뒤 다음 순서로 진행한다.

1. main의 최신 상태를 확인하고 독립 수정 브랜치를 사용한다.
2. 화면 유지·발행 성공 판정·시간 여유 수정을 구현하고 위 회귀 사례를 확인한다.
3. PR에 정확한 변경 파일, 검증 결과, 위험과 되돌리기 방법을 기록한다.
4. 필수 검증 통과 후 승인된 복구 범위에서 병합·배포하고 충분한 발행 여유가 있는 시간에 기존 작업을 실행한다.
5. 실제 공개 사이트의 6개 선택 구간, release_id, 슬롯, 데이터 기준 시각, 원장 공개 이력을 대조한다.
6. 검증용 장애 payload로 모든 구간 누락 상황을 다시 만들어, 이전 발행 카드 유지와 readiness 실패가 함께 성립함을 확인한다.
7. 운영 자료에 결과·커밋·실행 링크를 기록한다. 이후 슬롯 확인은 기존 watchdog을 사용하며 한 번의 성공으로 장기 가용성을 주장하지 않는다.

기존 모델·학습 규칙·백테스트 결과·발행 예측 값은 이번 변경 범위가 아니다.
운영 장애 복구와 예측 정확도 개선은 별도의 완료 기준을 적용한다.

되돌리기: 새 코드에 문제가 있으면 해당 수정 커밋을 revert하고 기존 작업으로 다음 발행을 복구한다.
발행 원장이나 과거 예측·정산 기록을 되돌리거나 덮어쓰지 않는다.
